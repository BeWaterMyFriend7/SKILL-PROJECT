# code-merge-helper 使用说明

## 适用场景

- 合并前预演或分析 merge、rebase、cherry-pick 已出现的冲突。
- 还原共同基线和双方改动意图，判断哪些行为必须保留。
- 识别文本冲突以及 Git 自动合并后的语义冲突。
- 生成人可审批、AI 可逐文件执行的解决方案，不改变代码或 Git 状态。

## 快速使用

~~~text
请使用 code-merge-helper 分析将远端 main 合并到当前分支的冲突，先不要执行。
~~~

## 它如何工作

Skill 会先在内部完成：

1. 确认当前侧、合入侧、common-base、SHA 和实际 stage 来源。
2. 相对 common-base 分别还原双方行为变化和改动目的。
3. 检查文本冲突、相关调用方和自动合并文件中的语义冲突。
4. 明确双方必须保留的行为及组合后的交互影响。
5. 选择保留一侧、语义融合或交给用户决定。
6. 形成逐文件动作，并按解决类型设计验证和停止条件。

报告先给人两部分：

- **合并结论：** 合并后保留哪些功能、整体如何处理及最高风险。
- **关键冲突：** 冲突实质、合并结果和需要决定的问题。

stage、SHA、关键证据、文件动作、验证和恢复方式放在后面的 **AI 冲突执行信息**。

## 核心规则

- 不凭 ours/theirs、提交时间或作者身份选择一侧。
- 不能只看冲突标记，必须检查语义冲突和相关调用方。
- 语义融合需要验证相关单侧行为和组合行为；简单文本冲突不虚构业务用例。
- 普通冲突一行表达，高风险、证据不足或需要决定时才展开。
- 没有内容的可选区块直接省略，状态只出现一次。
- 禁止在分析阶段编辑、暂存、提交或改变 Git 状态。
- 审批后也应逐文件暂存，禁止 `git add .`；避免宽泛破坏性恢复命令。
