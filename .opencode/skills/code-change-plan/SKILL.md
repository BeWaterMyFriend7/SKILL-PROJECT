# Code Change Plan

先回答目标如何实现、为什么这样改和影响什么，再给出可执行的实施与验收清单。

## 分析流程

1. 明确目标、验收标准、已确认决策、禁止范围和待决策问题。
2. 从现有代码、测试和接口合同还原当前行为；追踪入口、调用方、状态、配置、副作用及错误处理。
3. 按功能分析当前与目标差距、上下游影响及必须保持项；流程变化放在对应功能下。
4. 设计实现并解释真实取舍。涉及兼容、迁移、公共接口或职责调整时，说明其对审批决定的影响。
5. 从行为变化推导文件白名单和符号级动作；已有路径及符号须核实，新增对象明确标为“计划新增”，并核实所属目录、命名惯例和调用位置。
6. 按真实依赖安排实施；每阶段就地关联保持项、验证与完成条件。每项验证写前置条件、动作、预期结果；有依赖时写明承接结果及失败停止位置。
7. 按 [报告模板](assets/change-plan-template.md) 提炼结论与执行清单，输出后等待用户决定。

## 报告结构

报告分两层，审批人应不读执行区也能理解收益、影响、代价和待决策问题。

- **人类决策正文**：方案结论、行为变化与影响；存在重要设计选择时再写关键设计与取舍。
- **AI 实施与验收清单**：分析基线、范围、按依赖组织的文件/符号动作及对应验证、停止条件。简单任务只需一个实施单元，无须虚构多阶段。

正文优先使用功能语言；影响决策的接口名、配置字段和关键证据可以就地出现。执行细节集中在执行区，通过功能标题关联正文，避免重复解释结论。保持短句和清晰段落，不按句数机械拆分。表格适合比较，复杂流程就地补充示意或正反例。省略空的可选部分。

## 完成标准与边界

- 每个变化都有当前证据、目标行为、影响、保持项；每个文件动作能追溯到变化，每项验收有可判断的验证。
- 证据不足可输出暂缓方案，明确待核实项；不能编造路径、行为或已通过的验证。
- 只写用户指定的方案文档；未指定时写入下述默认位置，不修改被分析代码、配置、索引或提交历史。
- 用户要求仅在对话输出或禁止写文件时，直接在对话给出方案。
- 文件清单约束后续执行；范围扩大、基线或关键假设失效、需要新决策时停止并重新确认。批准方案不自动授权提交、推送或部署。
- 初始状态只标一次 `WAITING_FOR_APPROVAL`。报告中的验证是执行要求，未实际运行不得写成通过。
- 输出前检查：仅看正文是否能作出决定；执行区是否能落实该决定且保留必要约束。

## 输出

默认路径：`.code/change-plans/<需求描述>-YYYYMMDD-HHMMSS.md`。文件名去除路径分隔符和操作系统非法字符，重名时追加序号，不覆盖旧报告。
对话给出方案结论、最高风险、待决策项和报告链接。
可选编码工具见 [scripts/README.md](scripts/README.md)；编码检查不能证明方案语义正确。
