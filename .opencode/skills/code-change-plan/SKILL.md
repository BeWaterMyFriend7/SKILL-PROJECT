# Code Change Plan

先完整分析“怎么变化、影响什么”，再提炼成简短的人类决策正文和精确的 AI 执行清单。

## 工作流

1. 明确目标、验收标准、已确认决策、禁止范围和待决策问题。
2. 还原当前功能行为：入口、调用方、处理流程、数据或状态、配置、副作用、错误和现有测试。
3. 按功能点分析当前差距与目标变化；涉及调用链、状态流或执行顺序时，就地说明流程变化。
4. 沿上下游追踪影响，包括接口、调用方、消费者、兼容性、数据、配置、安全、运维、测试和文档。
5. 设计目标实现，明确模块职责、关键改动点、必须保持的行为和真实取舍。
6. 从功能变化和影响分析推导文件白名单，定位到文件、符号或配置项；只在存在依赖时安排实施顺序。
7. 为新行为、保持项、兼容性和风险设计可判断的验证；验证相互依赖时按阶段安排，并明确每个阶段承接的结果；定义需要停止并重新审批的情况。
8. 使用模板提炼报告，完成面向审批人的语言整理和快速阅读检查；状态设为 `WAITING_FOR_APPROVAL`，不修改业务代码。

## 分析完成标准

生成报告前必须满足：

- 每个功能变化都有当前证据、目标行为、主要影响和必须保持项。
- 每个受影响文件都能追溯到具体功能变化，不凭猜测提前列文件。
- 每项验收和重要保持项都有对应验证及预期结果。
- 范围不足、关键假设未经证实或存在真实取舍时，明确交给用户决定。

分析可以很详细，但不要把调查过程原样写入报告。

## 报告提炼

报告使用 `assets/change-plan-template.md`，面向技术负责人和审批人，分为两层：

1. **人类正文**
   - `方案结论`：先说明是否建议批准，再说明最终结果、主要影响和最高风险。
   - `关键变化`：按功能点说明当前情况、修改后行为和主要影响。
   - 只有真正影响实现或验收的问题才显示“需要决定”。
2. **AI 执行清单**
   - 按实施阶段组织完整的文件/符号级改动、不能破坏项、验证和停止条件。

内容规则：

- 先写结论，再解释做法。每句话只表达一个核心意思，优先使用“谁做什么”的主动句。
- 一个句子原则上不同时引入超过三个新概念。专业术语第一次出现时，用一句人话解释。
- 使用短段落，每段两到四句话。标题和加粗内容直接表达结论、变化、影响或风险。
- 表格只用于比较，单元格只写短句。复杂规则优先使用简短流程图、正反例或示意图。
- 实施方案按阶段组织。文件、类名和字段名只放在具体实施阶段，不进入方案主线。
- 一项事实只出现一次。调查过程和重复依据不进入报告。
- 流程变化只在确实涉及流程的功能点中出现，不创建空的流程章节。
- 没有内容的可选区块直接省略，不写“无”。
- 精确接口合同若影响人工决策，保留在关键变化附近；纯执行细节放入 AI 执行清单。
- 每项验证必须写清“前置条件、动作、预期结果”。验证较多或存在依赖时按阶段分组，写明承接上一阶段的结果、继续条件和失败后的停止位置。
- 输出前只阅读标题和加粗内容；如果不能理解主要结论、变化、影响和风险，就继续改写。
- 状态只出现一次，报告在最后一项有效内容后结束。

## 执行边界

- 文件清单是后续执行白名单；发现需要修改清单外文件时必须停止并重新审批。
- 不输出未经核实的路径、符号、命令或行为。
- 回滚或迁移要求只有在本次变化真实需要时才写入相关功能或停止条件。
- 只生成方案文档，不修改业务代码。

## 输出

- 文件：`.code/change-plans/<需求描述>-YYYYMMDD-HHMMSS.md`
- 初始状态：`WAITING_FOR_APPROVAL`
- 控制台只输出一句方案结论、最高风险、待决策项、状态和报告路径。

需要确保 Windows 下的 UTF-8 无 BOM 编码时，可使用 `scripts/write_utf8.py`。
