# Code Merge Helper

先还原共同基线和双方真实意图，判断哪些行为必须保留及如何组合，再提炼人类合并结论和 AI 冲突执行信息。

## 工作流

1. 确认操作类型、当前侧、合入侧、SHA、common-base、索引和工作区状态；有冲突索引时明确 stage-2、stage-3 的实际来源。
2. 识别 Git 标记出的文本冲突，并检查自动合并文件及相关调用方中的潜在语义冲突。
3. 相对 common-base 分别还原当前侧和合入侧的行为变化，使用代码、测试、文档和关键提交判断改动目的。
4. 为每个冲突明确当前侧必须保留、合入侧必须保留及两者同时存在时的组合行为，并追踪对接口、数据、配置、依赖和调用链的影响。
5. 基于证据选择保留当前侧、保留合入侧、语义融合或需要人工决策；证据不足不得猜测。
6. 形成逐文件、逐符号的解决动作、保护项和完成检查；只在存在依赖时安排顺序。
7. 按解决类型选择验证，检查相关单侧行为、组合行为、冲突标记和未合并索引；验证相互依赖时按阶段安排，并明确每个阶段承接的解决结果。
8. 使用模板提炼报告，完成面向审批人的语言整理和快速阅读检查；状态设为 `WAITING_FOR_APPROVAL`，不编辑文件、不暂存、不提交、不改变 Git 状态。

## 分析完成标准

生成报告前必须满足：

- 每个冲突都能说明共同基线、双方行为变化、必须保留项和推荐结果。
- 不能只看冲突标记；已检查签名、默认值、删除/重命名、配置、依赖、迁移、路由等语义影响。
- 每个解决动作都有证据和验证；语义融合必须覆盖相关单侧行为及组合行为。
- 双方意图互斥、证据不足或解决范围扩大时，明确交给用户决定。

详细判断规则见 `references/analysis-rules.md`。需要命令取证时读取 `references/git-command-reference.md`；设计验证时只选择 `references/verification-matrix.md` 中与本次解决类型和变更类型相关的内容。

## 报告提炼

报告使用 `assets/merge-resolution-report.md`，面向技术负责人和审批人，分为两层：

1. **人类正文**
   - `合并结论`：先说明是否建议继续合并，再说明合并后保留哪些功能、主要影响和最高风险。
   - `关键冲突`：用分支和功能语言说明冲突实质、合并结果以及需要决定的问题。
2. **AI 冲突执行信息**
   - Git 依据、按解决阶段组织的文件动作、验证、停止条件和当前状态适用的恢复方式。

内容规则：

- 先写结论，再解释处理方式。每句话只表达一个核心意思，优先使用“谁做什么”的主动句。
- 一个句子原则上不同时引入超过三个新概念。专业术语第一次出现时，用一句人话解释。
- 使用短段落，每段两到四句话。标题和加粗内容直接表达结论、冲突、影响或风险。
- 表格只用于比较双方变化，单元格只写短句。复杂组合行为优先使用简短流程图、正反例或示意图。
- 解决方案按阶段组织。文件、类名和字段名只放在具体解决阶段，不进入合并主线。
- 普通冲突一行表达；只有高风险、证据不足或难以理解的冲突才展开必要理由。
- 人类正文使用当前侧、合入侧和功能语言。stage、SHA 和提交日志放在 AI 区。
- 冲突结论只出现一次。调查过程和重复依据不进入报告。
- 每项验证必须写清“前置条件、动作、预期结果”。验证较多或存在依赖时按阶段分组，写明承接上一阶段的解决结果、继续条件和失败后的停止位置。
- 输出前只阅读标题和加粗内容；如果不能理解合并建议、冲突结果、影响和风险，就继续改写。
- 没有内容的可选区块直接省略，不写“无”。
- 状态只出现一次，报告在最后一项有效内容后结束。

## 执行边界

- 使用实际分支、提交和 stage 来源，不能仅凭容易混淆的 ours/theirs 表述。
- 禁止使用 `git add .`；审批后的执行也应逐个暂存已审核文件。
- 发现额外冲突、来源变化、证据不足、范围外修改或关键验证失败时必须停止。
- 避免 `reset --hard`、`checkout .`、`clean -fd` 等会覆盖无关工作的宽泛命令。
- 只生成分析报告，不修改代码、索引、分支或提交历史。

## 输出

- 文件：`.code/merge-review/合并分析-YYYYMMDD-HHMMSS.md`
- 初始状态：`WAITING_FOR_APPROVAL`
- 控制台只输出一句合并结论、冲突数、最高风险、待决策项、状态和报告路径。

需要确保 Windows 下的 UTF-8 无 BOM 编码时，可使用 `scripts/write_utf8.py`。
