# Git 冲突分析规则

本文件只定义三方取证、双方意图和语义冲突的判断方法；报告表达由模板负责，命令见 `git-command-reference.md`。

## 确认证据上下文

- 已存在冲突索引时，对比 common-base（stage-1）、当前侧（stage-2）和合入侧（stage-3）。
- 合并前预演没有 stage 内容时，对比 common-base、当前侧提交和合入侧提交，不伪造 stage 证据。
- rebase 或 cherry-pick 中 ours/theirs 容易与分支直觉相反，始终记录实际提交来源。
- 工作区已有修改、未合并索引和操作类型必须先确认，不能把无关差异当成冲突内容。

## 还原双方意图

对每侧分别回答：

1. 相对 common-base 改变了什么可观察行为。
2. 解决了什么问题，哪些测试或文档体现该目的。
3. 修改影响哪些调用方、接口、数据、配置或依赖。
4. 哪些行为是本侧必须继续成立的不变量。

证据优先使用当前代码、测试、接口合同和直接相关文档，再使用能证明意图的关键提交。提交时间、作者身份或单独一条 blame 记录不能证明业务目的。

## 检查语义冲突

即使 Git 自动合并成功，也要检查：

- 一侧修改函数签名，另一侧新增或保留旧调用。
- 一侧更改默认值、错误语义或执行顺序，另一侧依赖旧行为。
- 一侧删除或重命名符号，另一侧仍引用或修改旧位置。
- 两侧分别增加相同路由、配置键、依赖、迁移编号或生成入口。
- 两侧独立正确，但组合后破坏权限、安全过滤、幂等、并发或资源生命周期。
- 一侧修改生产代码，另一侧修改相关测试、文档或生成物，但合同不再一致。

## 选择解决方式

- **保留当前侧：** 合入侧变化已过时、与目标无关或其需求已由当前侧完整替代，并有证据支持。
- **保留合入侧：** 当前侧变化已过时、与目标无关或其需求已由合入侧完整替代，并有证据支持。
- **语义融合：** 两侧意图都有效且可同时成立；必须明确组合顺序、共享状态和交互边界。
- **需要人工决策：** 双方目标互斥、业务优先级未知、证据不足或选择会改变外部合同。

不得因为后提交、改动更多或作者更权威而选择一侧。

## 风险判断

- **高：** 安全控制、不可逆数据、公共 API、数据库/消息合同、核心链路、并发，或证据不足。
- **中：** 跨模块行为、配置、依赖、发布兼容或单模块外部行为变化。
- **低：** 局部实现或纯文本调整，外部行为和双方意图明确。

缺少关键验证、影响边界不清或无法证明双方意图时，风险至少提升一级。

## 必须停止

- stage、分支或 SHA 来源与分析时不一致。
- 出现未分析的新冲突或范围外修改。
- 无法证明一侧行为可以安全舍弃。
- 语义融合无法同时满足双方必须保留项。
- 关键验证失败或需要新的业务选择。
