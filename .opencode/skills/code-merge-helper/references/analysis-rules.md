# Git 冲突分析规则（简化版）

## 核心原则

1. **追溯改动原因** - 不仅看"改了什么"，更要理解"为什么改"
2. **三方对比** - 对比 common-base、stage-2、stage-3 的差异
3. **语义融合优先** - 优先保留两边的功能，而非简单二选一
4. **风险分级** - 使用 🔴 高 / ⚠️ 中 / ✅ 低 标记

## 冲突类型识别

### 文本冲突
Git 无法自动选择内容，在文件中留下冲突标记（`<<<<<<<`, `=======`, `>>>>>>>`）。

### 语义冲突（重点关注）
Git 自动合并成功，但组合后的行为可能错误。

**典型场景：**
- 一侧修改函数签名，另一侧新增调用
- 一侧更改默认值，另一侧依赖旧默认值
- 一侧删除字段，另一侧仍在引用
- 一侧重命名符号，另一侧在旧位置修改
- 两侧分别新增相同路由、配置项或数据库迁移编号

## 分析步骤

### 1. 识别改动内容
```bash
# 查看冲突文件
git diff --name-only --diff-filter=U

# 查看三方内容
git show :1:<file>  # common-base
git show :2:<file>  # stage-2 (当前分支)
git show :3:<file>  # stage-3 (合入分支)
```

### 2. 追溯改动原因
```bash
# 查看 stage-2 的提交历史
git log HEAD --oneline -- <file>

# 查看 stage-3 的提交历史
git log MERGE_HEAD --oneline -- <file>

# 查看具体提交
git show <commit-sha>
```

**关键问题：**
- 修改前的问题是什么？
- 修改改变了哪个行为？
- 修改的目的是什么？（性能、安全、功能、修复 bug）

### 3. 评估合并方案

**方案类型：**
- **保留 stage-2** - 保留当前分支改动
- **保留 stage-3** - 保留合入分支改动
- **语义融合** - 保留两边改动，合并语义
- **需人工决策** - 两边冲突，需要人工确认

**选择依据：**
- 优先保留能维持业务不变性的方案
- 优先保留测试充分的方案
- 优先保留兼容性好的方案
- 避免简单粗暴地选择"后提交"或"作者权威"

### 4. 风险评估

**风险等级：**
- 🔴 **高风险（5）** - 不可逆数据变更、安全控制、核心链路、证据不足
- 🔴 **高风险（4）** - 公共 API、消息、数据库、并发、发布兼容
- ⚠️ **中风险（3）** - 跨模块、配置、依赖变化
- ⚠️ **中风险（2）** - 单模块行为变化
- ✅ **低风险（1）** - 局部实现，无外部行为变化

**风险升级因素：**
- 影响公共 API 或跨模块边界 → 风险 +2
- 涉及并发、安全、数据持久化 → 风险 +1
- 缺少测试覆盖 → 风险 +1

## 推荐方案示例

### 示例 1: 缓存 + 安全加固（语义融合）

**场景：**
- stage-2: 添加了 Redis 缓存（性能优化）
- stage-3: 添加了密码过滤（安全加固）

**推荐方案：** 语义融合
```typescript
async findById(id: string) {
  // 1. 先查缓存（来自 stage-2）
  const cached = await redis.get(`user:${id}`);
  if (cached) return JSON.parse(cached);
  
  // 2. 查询数据库
  const user = await db.users.findOne({ id });
  
  // 3. 过滤密码（来自 stage-3）✅
  delete user.password;
  
  // 4. 写缓存（来自 stage-2）
  await redis.set(`user:${id}`, JSON.stringify(user));
  
  return user;
}
```

### 示例 2: 依赖版本冲突（需人工决策）

**场景：**
- stage-2: 添加 `redis@4.5.0`
- stage-3: 添加 `jsonwebtoken@9.0.2`

**推荐方案：** 合并两个依赖，Redis 版本根据 Node.js 版本确定

**人工决策：**
- Node.js < 18 → 用 redis@4.5.0
- Node.js >= 18 → 建议 redis@4.6.0

### 示例 3: 删除 vs 修改（保留删除）

**场景：**
- stage-2: 删除了旧模块（已完成迁移）
- stage-3: 修复了旧模块的 bug

**推荐方案：** 保留 stage-2（删除）

**理由：** 如果 stage-2 是计划内的模块迁移，stage-3 的修复已无意义

## 注意事项

1. **检查语义冲突** - 合并后运行编译和测试
2. **确认依赖兼容** - lockfile 冲突后需重新生成
3. **数据库迁移编号** - 检查是否有编号重复
4. **配置项冲突** - 确认新旧配置的兼容性
5. **测试覆盖** - 确保两边的功能都有测试

## 工具

```bash
# 检查冲突标记
git diff --check

# 查看未解决的冲突
git diff --name-only --diff-filter=U

# 查看文件的三方内容
git show :1:file  # base
git show :2:file  # ours
git show :3:file  # theirs
```
